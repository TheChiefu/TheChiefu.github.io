For some context, the program I am working on is a requirements gateway tool. So if you have requirements from say... So you can do some code testing in the main tool, link the test results to a requirement, and export back to your service.

Before I joined the gateway tool worked from an end-user's perspective (albeit slightly buggy) but was a nightmare in the backend to debug. I got frustrated with debugging and my manager told me how much pain it was for him as well, so I began thinking of solutions to the problem.

The primary issue I had was determining the `type` of data I was working on. In python you never have to declare what type your variable is. So a variable named "settings" could literally be anything: a string, a class object, int, whatever; and whoever wrote the program wrote things in a very C-like style. Sometimes camelcase, naming variables "m_Username", etc. I'm no python expert (this job is the first time I've actually used it), but even to me it seemed very messy and very "we got this to work and never touched it again".

At first I worked on adding typing to the variables, doing detective work in the debugger to determine what these variables are doing and if they are even named appropriately. As time went on, I do code reviews with my manager and we start to ruminate on new ideas to improve the code. We kept thinking to ourselves that even though the branches on adding hinting and cleaning up of files is good, that we'd be spending our time better doing a refactor. At the time we didn't have a clear view on what to do though, not until I did some more experimenting.

### My first big contribution
The first "big" branch I worked on was to help alleviate code debt by cleaning up how we managed user settings. Before I made any changes we'd save user settings to a file called "settings.json". Which was clear enough, pretty simple. However the way we read and loaded that data was a nightmare because our tool dealt with many possible gateway configurations. In theory a user could use all the available gateways supported by our linking tool, meaning the settings file contained settings for a possible 6 gateways at once. Again not inhertly bad but still... large.

In the code itself we read the settings file into a dictionary at high level. Then in each supported gateway read the settings object dictionary using keys. So if you wanted to retrieve the server name it'd look something like: `settings['codebeamer']['server_name']`.

Where you'd hope and pray that when you did that; that one, the settings dictionary actually existed; two, that the "codebeamer" dictionary existed; and three, that the "server_name" key existed and that its the type you'd want. Adding to the fact that we'd use different types (integers, string, etc) you'd have to already know what each key was trying to get.

So I embarked on making a dedicated "Settings" dataclass that contained all the common settings between all gateways and putting them in there. Making child dataclasses for each gateway for their specific settings. Adding properties with their expected types added as type-hints, methods to handle reading and writing to file, notify the user in the console if a field in their file is an invalid type or doesn't exist, and all that fun stuff. Basically making it so that anything related to settings was managed and done in that class so someone implementing new settings doesn't have to make any guesses.

Once that was a success, I then worked on fixing tracing in the program. Our tool is a little unique in that it can be used as a GUI application in Qt or in a command line. Before I made any changes, we'd write messages to the GUI using a method called "trace" in a "gui_handler.py" for **every** gateway (just reimplementing the same code every time), and sometimes that'd flow up to the gateway where it could **possibly** be shown in the command line.

I then got to work in ripping out all the duplicate code (around 1000 lines between all 6 gateways), and putting all the tracing logic into a new class I called "Advanced Trace Handler". Where (like the settings), it contained all the tracing relevant logic in it's own class. Writing to a specific log level, logging to specific files and levels (import logs, export logs, import error logs, and so on), adding date/timestamps, user specific settings like disabling/enabling debug calls, and so on. Again making it easier for us working on the program to debug and add new features. It was also had a nice addition of being usable to the end-users to add in their modifications of the program. That and we would trace everything easily to the GUI and console without any headaches since the logic is in one place now.

By the time I got those two big changes tested and implemented I started to think about fixing how we manage the GUI itself. The two big changes I mentioned before worked fine, but those were fixing issues in-place without doing much changes to the actual way we manage the GUI and data flow of the program. The main issues we had debugging were **helped** by patching over the issues with settings and tracing but it didn't **fix** the core issue of bad program architeture/design. What I noticed about the program what that things were organized oddly and somewhat arbitarily.

Using the **Codebeamer** gateway as an example, we'd have "codebeamer_gateway.py" as the main source of containing the settings file, GUI classes, and data handling classes. Then we'd have a "gui_handler.py" to handle GUI specific options that encompassed the `Auth -> Import -> Export` process we have in all gateways. A "data_handler.py" to handle data modification methods between all 3 processes in one place. Then for each step of the process do it all again "auth_gui_handler.py", "auth_data_handler.py" (x2). Which in theory isn't bad if you organize it well.

However, after I started digging through the code I noticed that the names rarely ever matched up with what they were actually doing. The "gui_handler" files would contain the Qt logic for creating buttons, line edits, and so on. But it'd also handle the button's click logic, incoming data from codebeamer, and so on. Then in the "data_handler" files I'd see sometimes it using Qt method for creating a popup box and again handling the incoming codebeamer data. By this point I kept thinking to myself, "there has to be a better way to do this"; especially since whoever designed the program kept throwing the variable `self` from one class into another class's method (when `self` should be implicit) and also into files where there was no class. The global functions whould just has an inexplainable and sometimes unused `self`.

### Game AI
At the same time as my other class I was also taking **Game AI**. Again I lucked out in that it uses Unity and I had the same professor as the first class, however unlike the first class this one went more in-depth with the topics that I not too familiar with.

The first class was more of watching a lecture, implement what you just watched or read, and repeat. This class was more, watch the lecture, read about the topic in depth, and spent hours or days trying to get a solution you think is good enough for the 2 auto-graded submissions you have. So a lot higher steaks and more "in the weeds" coding.

I thought it was very useful information though, even if the class almost pushed me over my limits sometimes (I had a few times were I felt like dropping the class). The topics we covered were:
- Discretized grid creation of a game world
- Path/Node Network navigation
- Nav Mesh creation (where nodes/portals are, nav-mesh agent radius, mesh boundaries)
- A* Search Implementation
